# ADR-0001: Render untrusted model output

Status: accepted

Date: 2026-10-01

## Context

Lesson JSON is generated by a language model. A `figure` block can carry inline SVG
markup or a mermaid diagram, and the model writes that content after reading web
search results, which are themselves untrusted. The model can therefore be induced to
emit markup that executes in the user's browser.

The backend documentation listed `svg` as an allowed `figure.kind` with no
sanitization requirement. `spec.md` states that web search results are untrusted and
page text goes to the model as data only, but nothing connected that rule to what
happens to the rendered result.

Inline `<svg>` can carry `<script>`, event handlers such as `onload`, and external
references. Mermaid's default configuration permits HTML labels and click callbacks.
Code blocks are lower risk but still model-authored text that must never be evaluated.

## Decision

Three rendering paths, one shared principle: **assume stored model output is hostile,
even after the backend has processed it.**

### Inline SVG

Defence in depth, two layers, using libraries with independent bug histories:

1. The backend sanitizes `figure.kind: svg` before the lesson is stored, using
   **`enshrined/svg-sanitize` pinned to `>=0.22.0`**. The pin is a floor, not a
   convenience.
2. The frontend sanitizes again with **DOMPurify**, `USE_PROFILES: { svg: true }`,
   before rendering. Separate library, separate codebase, separate bug history, so a
   bypass in one does not affect the other.

The second layer is not redundant. It exists because the first layer **will** be
bypassed again:

| CVE        | Affects                                       | Severity |
| ---------- | --------------------------------------------- | -------- |
| 2019-10772 | `<0.13.1`, `xlink` namespace mishandling      | high     |
| 2019-18857 | `<0.12.0`                                     | high     |
| 2022-23638 | `<0.15.0`                                     | medium   |
| 2023-28426 | `<0.16.0`                                     | medium   |
| 2025-55166 | `<0.22.0`, case-sensitive `xlink:href` bypass | medium   |

Five bypasses in the primary sanitizer's history, each found after deployment and each
requiring a version bump. `enshrined/svg-sanitize` is still the right choice: it is
mature, allowlist-based, and shipped by WordPress (`safe-svg`), Drupal, and TYPO3
core. The history is the argument for layer 2, not against the library.

Layer 2 also covers rows written before the sanitization rule existed, and any row
written by a path that skipped it.

**Do not remove layer 2 because layer 1 is present.** That is the one change this ADR
exists to prevent.

### Mermaid

Rendered in strict mode, with HTML labels and click callbacks disabled. Mermaid
output is parsed rather than injected.

### Code

Rendered as inert text. Never evaluated, never passed to a highlighter that evaluates
its input, never used to construct markup.

### Resource urls

Only `http` and `https` urls are followed, opened with `noopener` and `noreferrer`.

## Consequences

- The backend owns a sanitizer choice: **`enshrined/svg-sanitize` `>=0.22.0`**, with
  the version floor watched for advisories.
- The frontend owns a **DOMPurify** pass with the svg profile.
- SVG figures cost two sanitization passes rather than one, and a legitimate SVG may
  be over-sanitized into something visually wrong. Authors should prefer `mermaid` or
  `image` where they can.
- The frontend carries defensive code for output the backend claims to have cleaned.
  That is deliberate redundancy, not duplication to be refactored away.
- Security review of a new figure kind is a schema change, not a UI change.
